# Deployment, flow, plugin, and repository audit

Date: 2026-07-27
Scope: live Tdarr deployment, active flow `YR5PZ1QaD`, all installed Local
plugins, all deployed shared helpers, runtime/build/init assets, database
boundaries, and the separate public Git repository checkout.

## Executive outcome

The deployment was left running. No container restart/recreate, flow write,
plugin install, process termination, database maintenance, backup pruning,
FFmpeg build, GPU qualification workload, or job mutation was performed.

The active workflow is sophisticated and has several strong fail-closed
contracts, but it should not be treated as fully hardened. The review found:

- three active plugins with command-injection exposure through media paths;
- CPU VMAF-v1 production authority that accepts fewer geometries than the
  upstream resolver and lacks calibration/runtime attestation;
- ambiguous HDR classification that can irreversibly retag content as PQ;
- missing full-title decode validation after direct grain bitstream rewriting;
- GPU-lock ownership/reacquisition defects;
- severe host oversubscription and observed control-plane timeouts;
- an active/canonical graph mismatch that can halt a restarted container;
- redundant scanning, deep recurring health checks, weak retention, and
  public-network/auth configuration requiring reconsideration;
- raw application and learning databases that cannot safely be published.

The repository has been synchronized with current redacted source and runtime
assets, but only an aggregate-only learning database is publishable. A private
online backup is the correct interpretation of “update the DB” for the raw
state.

## Review method and coverage

Read-only live checks covered:

- container health, restart count, process tree, resource consumption, and

- mounted canonical graph and parity guard;

- library scan settings and auto-update settings;

Static source review covered:

- all 19 deployed runtime helpers;

- Community output handles used by the graph;
- init/install/parity/manifest/export tooling;

Forty-four runtime/plugin/helper JavaScript files passed `node --check` during
the live audit. The undeclared-identifier contract passed for the 19 VMAF
payloads present in the init mirror; that set includes inactive
`learnCQRanges` and does not cover the separately pinned filter/tools plugins.
These checks do not prove runtime quality or security.

## Priority findings

### P0 — security and output correctness

#### 1. Media-path shell injection

`extractVideoSamples`, `calculateVMAF`, and `selectBestParameters` interpolate
source or generated paths into shell command strings. Double-quoting does not
prevent POSIX command substitution through `$()` or backticks. Media names
from downloads are attacker-influenced, and production media mounts may be
writable.

Evidence:

- `plugins/vmaf/extractVideoSamples/1.0.0/index.js:6562,6650-6666`
- `plugins/vmaf/calculateVMAF/1.0.0/index.js:645-667,1035-1114`
- `plugins/vmaf/selectBestParameters/1.0.0/index.js:1309-1325,2998-3006`

Required repair: use `spawn`/`execFile` with explicit argv and `shell:false`;
validate executable selection separately; add filenames containing quotes,
spaces, `$()`, backticks, newlines, and leading dashes to tests.

#### 2. CPU VMAF-v1 authority is broader than its implementation

The resolver accepts general positive dimensions and chooses a metric family,
but `vmafV1Cpu` accepts narrow 1080/4K full-width/full-height bands. 720p,
1440p, SD, DCI/cropped, portrait, and missing/N/A SAR/DAR can fail only after
production authority is active. Capability preflight checks wrapper
executability rather than geometry, model, parser, and binary identity.

The active flow enables CPU-v1 production and provisional HDR. The helper
labels SDR runtime qualification incomplete and HDR provisional.

Evidence:

- `plugins/vmaf/_lib/vmafMetricContract.js:143-158,192-249,315-324`
- `plugins/vmaf/_lib/vmafV1Cpu.js:113-143,269-284,425-453`
- `plugins/vmaf/calculateVMAF/1.0.0/index.js:312-324,1350-1458`

Required repair: exact geometry/aspect preflight with a qualified fallback,
strict metric aliases, and a signed/versioned calibration artifact bound to
runtime hashes. Keep provisional HDR canary-only until validated.

#### 3. Ambiguous BT.2020 can be retagged as PQ

Unknown transfer plus BT.2020 primaries and 10/12-bit depth is treated as HDR,
then output tags are forced to BT.2020/PQ/BT2020NC. Missing static metadata only
warns.

Evidence: `plugins/vmaf/checkHdrContent/1.0.0/index.js:322-386`.

Required repair: preserve original signalling or fail for review unless HDR
transfer/profile evidence is affirmative.

#### 4. Direct film-grain output lacks full-title decode validation

The exported production path structurally inspects the rewritten output but
records that full-title decode validation was not performed, then may route it
to replacement. An older non-exported path had a bounded decode.

Evidence:

- `plugins/vmaf/synthesizeFilmGrain/1.0.0/index.js:3458-3467`
- `plugins/vmaf/synthesizeFilmGrain/1.0.0/index.js:3765,4024-4151`

Required repair: restore bounded distributed/full-title decode validation
after bitstream rewriting and before output 1/replacement.

### P1 — concurrency, graph, and ownership

#### 5. CPU scoring starves the control plane

`maxParallelCpuV1=2` applies per job, while `maxParallelVmaf=8` is reused as
threads per scorer. Each observed scorer also had two FFmpeg decoders. Four
staged flow jobs can multiply this beyond host capacity. The input label still
describes pre-FGS CAMBI CPU threads, obscuring its production VMAF-v1 role.

Required repair:

- global host-wide CPU-scoring semaphore;
- reserve 2–4 logical CPUs for Tdarr/Docker;
- separate `cpuV1ThreadsPerScore` from GPU/CAMBI concurrency;
- lower per-job concurrency pending measurement;
- expose queue pressure and scorer leases in the dashboard.

#### 6. GPU-lock release, reacquisition, and stale policy

The helper can break a same-file live lock without job/PID confirmation and
forces any lock older than eight hours stale. An arbitrary flow-provided
`lockDir` can later be recursively removed. `calculateVMAF` ignores its
internal `release()` result, blocks synchronously to reacquire, and reacquires
before CPU-only aggregation even though later graph stages have explicit
acquire nodes.

Evidence:

- `plugins/vmaf/_lib/gpuPipelineLock.js:26-55,284-315,381-439`
- `plugins/vmaf/calculateVMAF/1.0.0/index.js:243-303,2138-2155`
- `plugins/vmaf/acquireGpuPipelineLock/1.0.0/index.js:107-137`

Required repair: fixed/contained lock root, lease generation, owner-job
liveness, checked release, async wait, and no internal reacquire before
CPU-only work.

#### 7. Grain-analysis lock placement is unresolved

The active 34/53 graph routes HDR directly to grain analysis, so NVEncC KNN is
not globally serialized. A later host canonical inserted an acquire before the
whole plugin, producing 35/54. Tests and deploy tooling still require analysis
outside the lock, while a design tracker records under-protection but no real
contention measurement.

Holding the whole plugin would serialize roughly six minutes of mostly CPU
fitting. The preferred design is a narrow KNN lock inside the plugin or a
separate GPU stage. Measure first, then update flow, canonical, tests, parity,
and docs atomically.

#### 8. Active graph contains two routing defects

- Both `detectGPUEncoder` outputs go to HDR analysis, so no-GPU continues.
- `compareFileSizeRatioLive` exposes only output 1, but the graph also has an
  edge from output handle 2.

The repository intentionally preserves the redacted active snapshot. Fix both
in a versioned migration after drain.

#### 9. Flow/canonical mismatch can halt restart

At audit time:

| State | Nodes/edges | Grain-analysis lock | `maxParallelVmaf` |
|---|---:|---|---:|
| Active DB | 34/53 | none before analysis | 8 |
| Mounted host canonical | 35/54 | full plugin under lock | 4 |

The startup parity hook is fail-closed and explicitly stops the container
because the custom-init runner otherwise ignores failures. Recreate/restart is
unsafe until this is reconciled during an idle maintenance window.

The repository's two tracked snapshots now both represent the active 34/53
state. The unimplemented analysis-lock design is recorded here rather than
silently presented as live.

### P1 — data, deployment, and operations

#### 10. Raw databases and backups contain private material

The live flow table contained five real plaintext integration credentials;
twelve reviewed JSON backup snapshots also carried credential fields. The
learning DB contains media-identifying history. Values were deliberately not
printed or copied to Git.

The raw DB requested by the project owner was therefore not published. A
fresh aggregate-only database with minimum cohort 25 was generated instead.
Private raw backups must use SQLite online backup and encrypted storage.

#### 11. Recurrent health check performs deep GPU work

The live Docker health check launches real 8-bit and 10-bit CUDA KNN/toolchain
work every two minutes and has timed out under load. Health should mean cheap
API/TCP liveness. Run deep qualification at build/startup, manually after
runtime changes, or while idle.

#### 12. Library discovery is redundant

All four libraries enable filesystem events, 30-second folder polling, scan on
start, find-new scheduled scanning, and all 168 hourly schedule slots. This
adds enumeration load while the control plane is already timing out.

Choose one primary discovery mechanism and stagger a periodic reconciliation.
`holdFor=3600` hours is inactive because `holdNewFiles=false`; the real
seven-day authority is `checkFileAge`. Remove the misleading second setting.

#### 13. Exposure and automatic updates conflict with pinning

The live deployment had authentication disabled and ports bound on all
interfaces. Its internal node contacted `http://0.0.0.0:8266`. Server, node,
and plugin auto-update were enabled with `killAllProcessesDuringUpdate=true`.

After drain:

- enable authentication and limit interface exposure;
- set the internal endpoint to loopback;
- disable automatic replacement for the pinned custom stack;
- use a deliberate, canary-backed upgrade procedure.

#### 14. Retention is nearly exhausted or undefined

Job reports were approximately 98.5% of their configured 10 GiB limit. SQL
storage held 45 files and 2.824 GB, mostly one-off rollback databases, without
a visible retention policy.

Archive evidence privately before it is automatically lost. Do not prune
while jobs run. Define incident hold, count/age retention, verified restore,
and separate operational versus release backups.

## Remaining plugin-specific findings

Every installed Local identity is covered in
[Plugin and helper reference](plugin-reference.md). Additional notable items:

- `checkFileAge`: future timestamps can pass; first-seen state update races.
- `unmonitorRadarrOrSonarr`: external mutation lacks strong file/path identity
  and readback.
- grain plugins: symlink/canonical-path scope bypass.
- `checkCQBracket`: critical defaults are implicit.
- unused `checkFileLimits`: incorrect Tdarr file-size units and broken zero
  disable value.
- unused `checkVideoCodec`: first-stream and substring classification.
- `cleanupTempFiles`: trusts mutable paths and masks deletion failure.
- unused `detectSceneComplexity`: advertised scene analysis is not implemented.
- `exportVMAFResults`: CSV append races; SQLite should be authoritative.
- `fetchMediaMetadata`: year stripping, first-result matching, release-group
  parsing, and unbounded HTTP response issues.
- `learnCQRange`: pre-transcode false-success label and non-atomic CSV/EMA.
- unused `learnCQRanges`: incompatible selector shape.
- `monitorTranscodeRetry`: retry deletion lacks work-root containment.
- `vmafOptimizedTranscode`: hard timeout may kill legitimate long/slow titles,
  and documentation did not match its post-mux size rejection.

No separate material static defect was found in
`testEncodingParameters`, `checkCQRangeRetry`, or the standalone
`releaseGpuPipelineLock`; this is not equivalent to full runtime validation.

## Shared-helper findings

All 19 deployed helpers were reviewed. The highest-risk issues are in
`gpuPipelineLock`, `grainAnalysisArtifact`, `vmafMetricContract`, and
`vmafV1Cpu`.

`postEncodeCheckpoint` has a smaller crash window: retirement removes the
manifest before the artifact, so an interruption between those operations can
orphan a multi-gigabyte file. The checkpoint authentication/reuse design
otherwise fails closed.

`preFgsCambi.js` and `vmafV1Cpu.js` were previously omitted from deployment
parity despite being active production code. The repository verifier now
includes them and the tools plugin. The size-shadow model is deliberately not
published or included in parity because its categorical vocabulary contains
private media titles and release groups.

directory remains a deployment mirror; checkout parity is required to prevent
future drift.

## Recommended action order

### Before any new/untrusted workload

1. replace shell-string subprocesses with argv/no-shell APIs;
2. preserve/fail ambiguous HDR rather than retagging;
3. add CPU geometry/AR preflight and disable unsupported/provisional authority;
4. restore post-grain full-title decode validation;
5. contain all delete/lock paths.

### At the next drained maintenance window

1. create and verify private online DB backups;
2. reconcile live/canonical graph and remove invalid edges;
3. correct no-GPU routing;
4. disable automatic destructive updates;
5. deploy cheap health checks and dedicated scorer scratch;
6. lower CPU scoring pressure pending a global semaphore;
7. consolidate library scans;
8. archive reports and implement retention;
9. recreate once, run parity/deep qualification, then one canary.

### Design work requiring measurement

1. narrow grain KNN GPU locking;
2. calibrate CPU-v1 SDR/HDR authority by immutable runtime contract;
3. replace CSV/EMA concurrency with SQLite transactions;
4. strengthen Arr item identity and mutation verification;
5. set timeout/size policies from observed labeled outcomes.

## Validation boundary

This review establishes current source/state, static defects, consistency
checks, and observed resource pressure. It does not claim:

- that a current encode completed successfully merely because it entered the
  intended stage;
- that projected-size or CQ policies are validated;
- that CPU-v1 HDR is perceptually equivalent;
- that grain rewrite output is healthy without the missing full decode;
- that future jobs are safe until the critical path-injection issue is fixed.
