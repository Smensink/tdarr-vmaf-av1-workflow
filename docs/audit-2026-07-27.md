# Deployment, flow, plugin, and repository audit

Date: 2026-07-27; remediation continued 2026-07-28
Scope: live Tdarr deployment, active flow `YR5PZ1QaD`, all installed Local
plugins, all deployed shared helpers, runtime/build/init assets, database
boundaries, and the separate public Git repository checkout.

## Executive outcome

The baseline audit was read-only and left the deployment running. The later
remediation phase is recorded separately below and in
[live job forensics](live-forensics-2026-07-27.md); baseline observations in
this document remain labelled as observations rather than rewritten as if the
repaired state had always existed.

The active workflow is sophisticated and has several strong fail-closed
contracts, but it should not be treated as fully hardened. The review found:

- three active plugins with command-injection exposure through media paths;
- CPU VMAF-v1 production authority that accepts fewer geometries than the
  upstream resolver and lacks calibration/runtime attestation;
- ambiguous HDR classification that can irreversibly retag content as PQ;
- missing full-title decode validation after direct grain bitstream rewriting;
- GPU-lock ownership/reacquisition defects;
- severe host oversubscription and observed control-plane timeouts;
- an active/canonical graph mismatch that can halt a restarted container;
- a late cached node-plugin download that can undo custom-init pins;
- redundant scanning, deep recurring health checks, weak retention, and
  public-network/auth configuration requiring reconsideration;
- raw application and learning databases that cannot safely be published.

The working branch contains the current redacted source and runtime assets.
Its publication boundary includes final validation, the generated manifest,
the aggregate database, and the draft pull request. Only an aggregate-only
learning database is publishable; a private online backup is the correct
interpretation of “update the DB” for the raw state.

## Repository remediation update

The findings below describe the audited live snapshot. The repair branch
implemented the following corrections and the final immutable r3 release later
deployed them; the baseline findings remain dated forensic evidence:

- media-path subprocesses use literal argv with no shell boundary;
- CPU-v1 uses one shared geometry/model validator, exact rational SAR/DAR,
  reference/candidate transport equality, exact metric-alias enforcement, and
  GPU-v0 fallback before authority;
- ambiguous 10/12-bit BT.2020 with unknown transfer routes to keep-original
  instead of being retagged PQ;
- direct grain bitstream rewrites require complete AV1 decode before promotion
  and preserve the untouched original on validation failure;
- CPU-v1 is one task per job with two threads per score and a host-wide wrapper
  semaphore; unconfirmed internal GPU-lock release retains ownership, and
  explicit downstream Acquire nodes own the next GPU transition;
- the no-GPU and file-size routes now fail closed in the tracked graph.

CPU-v1 HDR remains uncalibrated and is disabled by the tracked flow policy;
operational throughput still needs controlled measurement, and unrelated
findings remain open unless separately noted.

The later drained deployment of the r3 subset is recorded in the dated rollout
record. That runtime qualification does not replace the withheld live canary.

The post-audit source also now:

- validates completeness against measured source/output packet counts instead
  of `fps × duration`;
- removes disposable producer-log paths from checkpoint identity and provides
  a strict retained-candidate migration;
- rejects and retires exact oversized post-mux checkpoints before replacement;
- makes CQ-bracketing and CQ-retry policy explicit in the Flow, and represents
  paired-CQ as force-full shadow with acting explicitly disabled;
- fixes future-time age handling, job-owned deletion boundaries, metadata
  matching/HTTP bounds, inactive plugin semantics, and learning telemetry;
- treats SQLite as authority and retires shared CSV/EMA mutation;
- supervises early FFmpeg exit so NVEncC cannot remain hidden behind an
  API-idle worker;
- requires both API-idle and real-process/GPU-lock absence before deployment or
  denoise trials;
- binds Arr unmonitor mutations to one path-verified movie/episode-file
  identity and requires a `monitored=false` readback.
- uses one exact delivered-size policy: a 30% search target, 20% minimum
  delivered reduction, and 80% maximum final output/source ratio;
- separates the unvalidated 90% projected-size research boundary from
  delivered success;
- records usable base encodes as durable `candidate_ready` state, not success,
  and leaves `met_vmaf_target` null for technical failure;
- validates the final candidate, performs journaled attested replacement, and
  makes the finalizer the sole delivered-success authority;
- retains a permanent authenticated retirement tombstone before removing the
  delivered journal and post-encode checkpoint inventory.

### P1 — concurrency, graph, and ownership

#### 5. CPU scoring starves the control plane

`maxParallelCpuV1=2` applies per job, while `maxParallelVmaf=8` is reused as
threads per scorer. Each observed scorer also had two FFmpeg decoders. Four
staged flow jobs can multiply this beyond host capacity. The input label still
describes pre-FGS CAMBI CPU threads, obscuring its production VMAF-v1 role.

Required repair:

- global host-wide CPU-scoring semaphore;
- reserve 2–4 logical CPUs for Tdarr/Docker;
- separate `cpuV1ThreadsPerScore` from GPU/CAMBI concurrency;
- lower per-job concurrency pending measurement;
- expose queue pressure and scorer leases in the dashboard.

#### 7. Grain-analysis lock placement

### P1 — data, deployment, and operations

#### 10. Raw databases and backups contain private material

The live flow table contained five real plaintext integration credentials;
twelve reviewed JSON backup snapshots also carried credential fields. The
learning DB contains media-identifying history. Values were deliberately not
printed or copied to Git.

The raw DB requested by the project owner was therefore not published. A
fresh aggregate-only database with minimum cohort 25 was generated instead.
Private raw backups must use SQLite online backup and encrypted storage.

#### 11. Recurrent health check performs deep GPU work

The live Docker health check launches real 8-bit and 10-bit CUDA KNN/toolchain
work every two minutes and has timed out under load. Health should mean cheap
API/TCP liveness. Run deep qualification at build/startup, manually after
runtime changes, or while idle.

The old preflight was subsequently observed starting GPU smoke work while an
encode held the pipeline lock. A minimal mounted guard immediately made the
legacy probe skip both GPU tests while that exact lock was present; a 09:32Z
health run confirmed the skip. The final checked-in preflight removes the
remaining check/run race: a dedicated runner either takes and holds the same
non-stealing token/generation-owned `TDARR_GPU_PIPELINE_LOCK_DIR` lease through
both tests, or skips without touching an existing owner. The next drained
recreate still replaces this legacy deep health check with the cheap TCP check
from the example Compose configuration.

#### 12. Library discovery is redundant

All four libraries enable filesystem events, 30-second folder polling, scan on
start, find-new scheduled scanning, and all 168 hourly schedule slots. The
30-second fallback and startup scan add enumeration load while the control
plane is already timing out. However, the media roots are Windows bind mounts
inside Docker, where filesystem notifications are not sufficient evidence to
remove periodic reconciliation.

Keep filesystem events and the hourly scheduled find-new scan, increase the
folder-watch interval to 300 seconds, and disable only scan-on-start. Preserve
the existing `holdFor=3600` value: even though `holdNewFiles=false` made it
inactive in the observed snapshot, there is not enough evidence to prove that
removing the hour is safe for every in-progress import path.

#### 13. Exposure remains; automatic updates are currently disabled

The audited deployment had authentication disabled and ports bound on all
interfaces. Its internal node contacted `http://0.0.0.0:8266`.

A later live re-verification found the pinned-runtime update controls already
disabled:

- `autoUpdateNodes=false`;
- `autoUpdateServer=false`;
- `pluginAutoUpdate=false`;
- `killAllProcessesDuringUpdate=false`;
- descriptor-bound `/run/s6/container_environment/cronPluginUpdate` was
  zero-byte;
- descriptor-bound
  `/run/s6/container_environment/enableDockerAutoUpdater` was exactly
  `false`; and
- `TDARR_FLOW_PARITY_BOOTSTRAP` was absent and therefore normalized to
  effective zero.

S6 PID 1 does not retain the service environment as an authoritative
`/proc/1/environ` snapshot. Recovery therefore authenticates those S6
container-environment entries with no-follow descriptor reads and separately
validates `Tdarr_Node_Config.json` and `Tdarr_Server_Config.json` as canonical,
single-link, safely owned and permissioned, bounded strict UTF-8/no-BOM files
with exactly one own empty `cronPluginUpdate` key.

These current values close the previously suspected automatic-replacement
race, but they are mutable runtime evidence rather than a permanent guarantee.
Retained-candidate recovery must record and re-prove the complete environment,
configuration, and settings contract before the private request is compiled
and again immediately before dispatch. A mismatch blocks recovery. The
recovery operation must not mutate updater settings.

After drain:

- enable authentication and limit interface exposure;
- set the internal endpoint to loopback;
- re-prove and preserve the disabled update state above; and
- use a deliberate, canary-backed upgrade procedure.

Rollout resolution (2026-07-28): authentication is enabled, published ports and
the internal-node endpoint are loopback-only, and unauthenticated API access is
rejected. The controlled live canary remains outstanding for the queue-
isolation reason recorded in the r3 rollout evidence.

#### 14. Retention is nearly exhausted or undefined

Job reports were approximately 98.5% of their configured 10 GiB limit. SQL
storage held 45 files and 2.824 GB, mostly one-off rollback databases, without
a visible retention policy.

Archive evidence privately before it is automatically lost. Do not prune
while jobs run. Define incident hold, count/age retention, verified restore,
and separate operational versus release backups.

#### 15. Post-init node plugin download can undo the pinned catalog

The remediation restart exposed a second catalog authority. Custom init first
seeded and patched the internal-node catalog correctly, but Tdarr_Node then
downloaded the server's older cached `nodePlugins.Zip`. Twenty-seven Local
execution copies reverted while their mounted source and persistent-server
copies remained current; the separately hotfixed VMAF helper was the only
affected node copy still current. The fresh dispatch compiler detected the
mixed generation and refused to queue the retained-candidate retry.

This is not fixed by copying files earlier or by omitting an application
restart. The checked-in r3 init now:

1. seeds the complete persistent server catalog into the internal node;
2. applies every pinned plugin/helper;
3. fixes ownership;
4. creates the exact
   `/app/Tdarr_Node/assets/app/plugins/.git` directory that Tdarr_Node itself
   recognizes as its development-preservation interlock; and
5. makes startup parity require that safe sentinel plus all source/server/node
   hashes.

After reconnect, parity must pass twice at least 15 seconds apart while global
and node admission remain closed. This design deliberately disables automatic
plugin download for the bundled pinned node. Future catalog changes are
maintenance-window, full-seed recreates rather than live partial copies.

Rollout resolution (2026-07-28): the full 359-file
persistent-server/internal-node catalog was reconciled,
`FlowHelpers/1.0.0/hardwareUtils.test.js` was restored for Tdarr_Node's
enabled-FFmpeg-encoder probe, and the two required delayed parity passes
succeeded while admission remained closed.

## Validation boundary

This review establishes current source/state, static defects, consistency
checks, and observed resource pressure. It does not claim:

- that a current encode completed successfully merely because it entered the
  intended stage;
- that projected-size or CQ policies are validated;
- that CPU-v1 HDR is perceptually equivalent;
- that a live grain rewrite completed its required exhaustive decode merely
  because the static/source contract requires one;
- that provisional CPU-v1 HDR or future stronger-denoise contracts are
  production-authorized without separate controlled evidence.

Stronger-denoise evaluation remains sample-only, manual-review-only, and
non-promoting. It applies only to selected original-preserved candidates;
already replaced AV1 outputs must not be used for second-generation trials.
The two 2026-07-28 screens were unavailable before valid comparison output and
support no denoise or size conclusion.
